
###Analysis

**Patrón observado en logs (100% de las invocaciones):**

```
RiskAnalysis:
  lambda RiskAnalysis
  event: {'credit_id': 'canary-credit-XXXXXXXXXX'}
  response dynamodb:  <--- lectura OK, status=pending
  Invocando endpoint processor   <--- ULTIMA linea antes del timeout
  REPORT Duration: 10000.00 ms  Status: timeout   <--- timeout siempre exacto

CreditEvaluation:
  Se guarda solicitud en dynamodb con status=pending  <--- escribe OK
  Registro XXXX guardado con estado=pending
  REPORT Duration: 10000.00 ms  Status: timeout   <--- tambien termina en timeout
  [NUNCA se registra "status_code:"]
```

**Causa raiz - dos problemas encadenados:**

**Problema 1 (causa directa del timeout):** `src/risk/app.py:37`

```python
processor_response = requests.get(PROCESSOR_URL)  # sin timeout
```

`requests.get` sin parametro `timeout` bloquea indefinidamente hasta que el SO cierre la conexion. El endpoint `PROCESSOR_URL` no responde dentro de los 10 segundos del Lambda. Esto mata la ejecucion antes de llegar al `return`.

**Problema 2 (falla de diseño - nunca actualiza el estado):** `src/risk/app.py:40`

```python
return {"statusCode": 200, "body": json.dumps(response["Item"])}
```

El `RiskAnalysis` solo **lee** el item de DynamoDB y llama al processor, pero **nunca escribe** de vuelta el estado actualizado (`approved`, `rejected`, etc.). Falta un `table.update_item(...)` antes del `return`. Incluso si el timeout fuera corregido, el estado nunca pasaria de `pending`.

**Flujo con el bug:**

```
CreditEvaluation → guarda pending en DynamoDB → invoca RiskAnalysis (sincrono)
  RiskAnalysis → lee DynamoDB (pending) → llama PROCESSOR_URL (cuelga) → timeout 10s
    → nunca actualiza DynamoDB
  CreditEvaluation → esperando respuesta → timeout 10s (status_code: nunca se imprime)
    → nunca actualiza DynamoDB
Estado final: pending para siempre
```

**Steps to reproduce:**
1. Enviar cualquier solicitud de credito al endpoint de `CreditEvaluation`
2. `PROCESSOR_URL` no responde en menos de 10 segundos
3. Ambos Lambdas terminan en timeout; DynamoDB permanece con `status=pending`

**Expected vs Actual:**
- Esperado: `pending` → (RiskAnalysis evalua) → `approved` o `rejected`
- Actual: `pending` → timeout → `pending` (para siempre)

**Archivos/funciones afectados:**
- `src/risk/app.py:37` — `requests.get(PROCESSOR_URL)` sin timeout
- `src/risk/app.py:40` — return sin actualizar el estado en DynamoDB

---

### Solution

**Fix 1 — agregar timeout al HTTP call (`src/risk/app.py:37`):**
```python
processor_response = requests.get(PROCESSOR_URL, timeout=5)
```
Esto permite manejar la excepcion `requests.exceptions.Timeout` en el bloque `except` existente y retornar un error controlado a `CreditEvaluation`.

**Fix 2 — actualizar el estado en DynamoDB antes del return (`src/risk/app.py`, entre lineas 37-40):**
```python
risk_result = processor_response.json()  # resultado del procesador externo
new_status = risk_result.get("status", "rejected")

table.update_item(
    Key={"credit_id": credit_id},
    UpdateExpression="SET #st = :status",
    ExpressionAttributeNames={"#st": "status"},
    ExpressionAttributeValues={":status": new_status},
)
```

Sin este segundo fix, incluso solucionando el timeout, el estado nunca saldria de `pending`.
