###Analysis

**Evidencia en los logs** (`/aws/lambda/test-016-transfer-processor`)

El patrón se repite en cada ciclo de 5 minutos. Ejemplo del ciclo 18:55:

```
18:55:15  TXN: 98aef3f9 | SRC: A | DST: B | STATE: START
18:55:15  TXN: bf7be3c4 | SRC: B | DST: A | STATE: START
18:55:15  TXN: 98aef3f9 | RES: A | PH: 1 | STATE: RESERVED   <- lock A adquirido
18:55:15  TXN: bf7be3c4 | RES: B | PH: 1 | STATE: RESERVED   <- lock B adquirido
18:55:30  TXN: 98aef3f9 | RES: B | PH: 2 | STATE: ATTEMPT    <- esperando B (tomado por bf7be3c4)
18:55:30  TXN: bf7be3c4 | RES: A | PH: 2 | STATE: ATTEMPT    <- esperando A (tomado por 98aef3f9)
18:56:14  REPORT ... Duration: 60000 ms ... Status: timeout   <- ambas instancias timeout
```

Los dos lambdas mueren sin liberar los recursos. El mismo patrón ocurre en todos los ciclos observados (18:20, 18:25, 18:30, 18:35, 18:40, 18:45, 18:50, 18:55).

**Flujo de ejecución problemático**

`transfer_funds.py` adquiere locks en orden: fuente → destino:

```
# transfer_funds.py:28
reserve_resource(f"res:{source}", tx_id)   # PH: 1 — lock sobre cuenta origen
verify_settlement_window(source)            # llamada externa (demora ~15s)
# transfer_funds.py:34
reserve_resource(f"res:{target}", tx_id)   # PH: 2 — intenta lock sobre cuenta destino
```

Cuando A→B y B→A corren simultáneamente:

| TXN A→B           | TXN B→A           |
|-------------------|-------------------|
| lock("res:A") ✓   | lock("res:B") ✓   |
| espera lock("res:B") → | espera lock("res:A") → |
| **bloqueado**     | **bloqueado**     |

**Por qué el deadlock no se resuelve solo**

`resource_registry.py:13-26` — la función `reserve_resource` tiene un loop infinito sin timeout ni límite de reintentos:

```python
def reserve_resource(resource_key, tx_id):
    while True:                          # <- bucle sin condición de salida
        try:
            table.put_item(...)
            return True
        except ConditionalCheckFailedException:
            time.sleep(0.1)             # espera 100ms y reintenta para siempre
```

Lambda muere por timeout (60 s). El bloque `except` de `transfer_funds.py:46-49` nunca se ejecuta porque el timeout de Lambda interrumpe la ejecución antes de llegar al `release_resource`. Los items en DynamoDB quedan con TTL de 300 s, pero el TTL de DynamoDB es de eliminación eventual (puede tardar horas), bloqueando transacciones subsiguientes.

**Ubicación del bug**

| Archivo | Línea | Problema |
|---|---|---|
| `src/resource_registry.py` | 13 | `while True` sin timeout — espera infinita |
| `src/transfer_funds.py` | 28-34 | Adquisición de locks en orden variable según la dirección de la transferencia |

**Ejemplo de ejecución**

- Entrada TXN-1: `{ from_account: "A", to_account: "B" }`
- Entrada TXN-2: `{ from_account: "B", to_account: "A" }`
- Esperado: una de las dos transacciones falla/espera y la otra completa
- Real: ambas adquieren su primer lock, ambas esperan el segundo → deadlock → timeout → locks quedan en DynamoDB bloqueando operaciones futuras

---

### Solution

**1. Agregar timeout en `reserve_resource` (archivo: `src/resource_registry.py`)**

El loop `while True` debe tener una condición de salida basada en tiempo:

```python
def reserve_resource(resource_key, tx_id, timeout_s=10):
    start = time.time()
    while time.time() - start < timeout_s:
        try:
            table.put_item(...)
            return True
        except ConditionalCheckFailedException:
            time.sleep(0.1)
    raise TimeoutError(f"No se pudo reservar {resource_key} en {timeout_s}s")
```

Esto permite que el `except` de `transfer_funds.py:46` se ejecute y libere el primer lock.

**2. Ordenar locks por clave canónica (archivo: `src/transfer_funds.py`)**

Adquirir siempre los locks en el mismo orden global (ej. alfabético), independientemente de quién es origen y quién es destino. Esto rompe la condición de espera circular:

```python
first, second = sorted([f"res:{source}", f"res:{target}"])
reserve_resource(first, tx_id)
reserve_resource(second, tx_id)
```

Con esta estrategia, tanto A→B como B→A siempre intentan adquirir `res:A` antes que `res:B`, eliminando el deadlock.
