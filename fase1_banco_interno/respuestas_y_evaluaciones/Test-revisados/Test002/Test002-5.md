

###Analysis

## Hallazgos en los Logs

Tras analizar los logs de CloudWatch, se identificó un patrón crítico de errores:

**Error recurrente encontrado:**
```
ERROR Invoke Error {"errorType":"TypeError","errorMessage":"fetch failed","cause":{"errorType":"SocketError","errorMessage":"other side closed","code":"UND_ERR_SOCKET"}}
```

**Patrón identificado:**
- Todas las ejecuciones siguen el mismo flujo defectuoso
- Se recibe correctamente el callback: `PAYMENT_CALLBACK_RECEIVED { transaction_id: 'TRX_CANARY_XXXXX' }`
- El error ocurre consistentemente en la línea 28 del archivo `SavePayment.js`
- Los errores de socket indican conexiones cerradas prematuramente por el servidor externo
- Las direcciones IP de destino varían (3.167.56.70, 3.167.56.113, 3.167.56.46) sugiriendo un balanceador de carga

## Relación con el Código Fuente

Analizando el archivo `SavePayment.js`, se identifica la **causa raíz** en el flujo de ejecución:

```javascript
// Línea 28 - Primera llamada fetch (obtener información del pago)
const response = await fetch(externalPaymentServiceUrl.replace(":id", transactionId), {
    method: "GET",
    headers: {
        "Content-Type": "application/json"
    }
});

// Líneas 30-38 - GUARDADO EN BASE DE DATOS (se ejecuta sin validar la respuesta anterior)
await docClient.send(new PutCommand({
    TableName: tableName,
    Item: {
        transaction_id: transactionId,
        payment_status: "success",  // ← PROBLEMA: Se marca como exitoso sin validación
        order_status: "paid",
        processed_at: new Date().toISOString()
    }
}));

// Línea 44 - Segunda llamada fetch (confirmación)
const confirmationResponse = await fetch(externalPaymentServiceConfirmationUrl.replace(":id", transactionId), {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    }
});
```

**Problema identificado:**
1. La primera llamada `fetch` falla (línea 28) debido a errores de socket
2. **El código NO valida si la primera llamada fue exitosa**
3. Se procede a guardar el pago en DynamoDB marcándolo como `"success"` sin verificar el estado real
4. La segunda llamada `fetch` nunca se ejecuta debido al error anterior

## Ejemplo de Ejecución

**Flujo actual (defectuoso):**
```
1. Recibe callback: transaction_id = "TRX_CANARY_d72de7"
2. Intenta GET a plataforma externa → FALLA (SocketError)
3. ❌ No valida respuesta
4. Guarda en DB: payment_status = "success" ← INCORRECTO
5. ❌ Nunca ejecuta confirmación POST
6. Retorna 200 con "db_status": "success"
```

**Flujo esperado (correcto):**
```
1. Recibe callback: transaction_id = "TRX_CANARY_d72de7"
2. GET a plataforma externa → Valida estado real del pago
3. Si pago exitoso → Guarda en DB con status correcto
4. POST confirmación a plataforma externa
5. Retorna respuesta basada en validaciones reales
```

## Soluciones Propuestas

### Solución Principal: Validación de Respuestas y Manejo de Errores

```javascript
exports.handler = async (event) => {
    console.info("RAW_EVENT", JSON.stringify(event));

    const transactionId = event.queryStringParameters?.transaction_id;
    const tableName = process.env.TABLE_NAME;

    if (!transactionId) {
        console.error("MISSING_TRANSACTION_ID");
        return {
            statusCode: 400,
            body: JSON.stringify({ error: "transaction_id is required" })
        };
    }

    console.info("PAYMENT_CALLBACK_RECEIVED", { transaction_id: transactionId });

    try {
        // 1. VALIDAR ESTADO DEL PAGO EN PLATAFORMA EXTERNA
        const response = await fetch(externalPaymentServiceUrl.replace(":id", transactionId), {
            method: "GET",
            headers: {
                "Content-Type": "application/json"
            }
        });

        // VALIDACIÓN CRÍTICA: Verificar respuesta exitosa
        if (!response.ok) {
            console.error("EXTERNAL_PAYMENT_CHECK_FAILED", {
                status: response.status,
                statusText: response.statusText,
                transaction_id: transactionId
            });
            
            // Guardar como fallido
            await docClient.send(new PutCommand({
                TableName: tableName,
                Item: {
                    transaction_id: transactionId,
                    payment_status: "failed",
                    order_status: "payment_verification_failed",
                    processed_at: new Date().toISOString(),
                    error_reason: `External service returned ${response.status}`
                }
            }));

            return {
                statusCode: 500,
                body: JSON.stringify({
                    transaction_id: transactionId,
                    db_status: "failed",
                    error: "Payment verification failed"
                })
            };
        }

        // 2. OBTENER Y VALIDAR DATOS DEL PAGO
        const paymentData = await response.json();
        
        // Validar que el pago realmente fue exitoso
        const isPaymentSuccessful = paymentData.status === 'completed' || paymentData.status === 'success';
        
        // 3. GUARDAR EN BASE DE DATOS CON ESTADO REAL
        await docClient.send(new PutCommand({
            TableName: tableName,
            Item: {
                transaction_id: transactionId,
                payment_status: isPaymentSuccessful ? "success" : "failed",
                order_status: isPaymentSuccessful ? "paid" : "payment_failed",
                processed_at: new Date().toISOString(),
                external_payment_data: paymentData
            }
        }));

        console.info("LOCAL_PAYMENT_PERSISTED", {
            transaction_id: transactionId,
            status: isPaymentSuccessful ? "success" : "failed"
        });

        // 4. CONFIRMAR SOLO SI EL PAGO FUE EXITOSO
        if (isPaymentSuccessful) {
            const confirmationResponse = await fetch(externalPaymentServiceConfirmationUrl.replace(":id", transactionId), {
                method: "POST",
                headers: {
                    "Content-Type": "application/json"
                }
            });

            console.info("CONFIRMATION_RESPONSE", {
                status: confirmationResponse.status,
                statusText: confirmationResponse.statusText,
                transaction_id: transactionId
            });
        }

        return {
            statusCode: 200,
            body: JSON.stringify({
                transaction_id: transactionId,
                db_status: isPaymentSuccessful ? "success" : "failed",
                payment_verified: true
            })
        };

    } catch (error) {
        console.error("PAYMENT_PROCESSING_ERROR", {
            transaction_id: transactionId,
            error: error.message,
            stack: error.stack
        });

        // Guardar como error en base de datos
        await docClient.send(new PutCommand({
            TableName: tableName,
            Item: {
                transaction_id: transactionId,
                payment_status: "error",
                order_status: "processing_error",
                processed_at: new Date().toISOString(),
                error_message: error.message
            }
        }));

        return {
            statusCode: 500,
            body: JSON.stringify({
                transaction_id: transactionId,
                db_status: "error",
                error: "Payment processing failed"
            })
        };
    }
};
```

### Soluciones Complementarias:

1. **Configurar reintentos con backoff exponencial** para las llamadas fetch
2. **Implementar timeout** en las llamadas HTTP
3. **Agregar logs detallados** para mejor trazabilidad
4. **Implementar webhook de reconciliación** para verificar pagos pendientes
5. **Configurar alertas** para errores de socket recurrentes

La causa raíz es la **falta de validación del estado real del pago** antes de marcarlo como exitoso en la base de datos, combinado con **manejo inadecuado de errores de red**.
