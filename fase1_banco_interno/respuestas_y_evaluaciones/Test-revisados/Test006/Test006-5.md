### Analysis

**Flujo de eventos confirmado por los logs (ejemplo PROD-555):**

| Timestamp | Lambda | Evento |
|-----------|--------|--------|
| `10:00:38.323` | `UpdatePriceFunction` | Precio actualizado en DynamoDB: `nuevoPrecio=65.0` |
| `10:00:40.238` | `InventoryCheckFunction` | **ERROR**: `precioQueMostroCache=162`, `precioRealEnDB=65.0`, `diferencia=97.0` |
| `10:00:54.692` | `CacheInvalidationFunction` | Cache eliminado: `cacheEliminado=true` |

La invalidacion del cache ocurre **+16 segundos** despues del cambio de precio. Durante esa ventana cualquier checkout usa el precio viejo del cache (162) pero `InventoryCheck` lee el precio nuevo de DynamoDB (65) → rechazo por "precio manipulado".

**Pasos de reproduccion:**
1. `UpdatePrice` escribe el nuevo precio en DynamoDB (ej: 65.0)
2. DynamoDB Stream dispara `CacheInvalidationFunction` de forma asincrona
3. `CacheInvalidationFunction` ejecuta `requests.get(PROCESSOR_API_URL)` **sin timeout** — esta llamada HTTP demora ~14-15 segundos
4. Mientras tanto, `ProductPricingFunction` sirve el precio viejo desde Redis (ej: 162.0) a usuarios que consultan el producto
5. El usuario envia el checkout con `price=162`
6. `InventoryCheckFunction` lee DynamoDB (precio=65) → `abs(162 - 65) = 97 > 0.01` → retorna `"Precio manipulado o desactualizado"`

**Esperado vs. Actual:**

- Esperado: cache eliminado inmediatamente al cambiar el precio en DynamoDB
- Actual: cache eliminado ~14-16 segundos despues, por la llamada HTTP bloqueante previa

**Ubicacion del bug:**

`cache_invalidation/app.py`, lineas 41-50:

```python
# PROBLEMA: la llamada HTTP bloquea la ejecucion ~14s antes de eliminar el cache
try:
    response = requests.get(PROCESSOR_API_URL)  # bloquea sin timeout
    ...
except Exception as e:
    logger.error("Error llamando a API externa", error=str(e))

cache_key = f"price:{product_id}"
deleted = redis_client.delete(cache_key)  # se ejecuta 14s tarde
```

---

### Solution

**Mover la eliminacion del cache al inicio del handler**, antes de la llamada HTTP externa. La invalidacion debe ser inmediata y no puede estar condicionada por servicios de terceros.

```python
# CORRECTO: eliminar cache primero, luego ejecutar la llamada HTTP
cache_key = f"price:{product_id}"
deleted = redis_client.delete(cache_key)

logger.info(
    "Cache invalidado", productId=product_id, cacheEliminado=bool(deleted)
)

try:
    response = requests.get(PROCESSOR_API_URL, timeout=5)
    ...
except Exception as e:
    logger.error("Error llamando a API externa", error=str(e))
```

**Cambios requeridos en `cache_invalidation/app.py`:**

1. Mover `redis_client.delete(cache_key)` a antes de `requests.get(PROCESSOR_API_URL)` — esto elimina la ventana de inconsistencia.
2. Agregar `timeout=5` (o similar) al `requests.get()` — sin timeout, si `PROCESSOR_API_URL` cuelga, la Lambda agota su tiempo de ejecucion y el cache tampoco se elimina.

**Evidencia adicional en los logs:** Se observan pares de eventos de CacheInvalidation por producto (ej: PROD-485 `cacheEliminado=true` a las `10:05:44`, luego `cacheEliminado=false` a las `10:05:59`). El segundo evento con `false` confirma que el DynamoDB Stream dispara el evento dos veces (duplicados), pero no representa el problema principal ya que el `true` confirma que la eliminacion ocurre. El problema es exclusivamente el **orden**: HTTP antes que delete.
