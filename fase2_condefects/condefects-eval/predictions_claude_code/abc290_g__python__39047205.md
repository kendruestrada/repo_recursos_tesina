Analizando el algoritmo: `solve1` recorre las denominaciones `tmp[j]` (sumas prefijo de potencias de `k`) de mayor a menor y va extrayendo cuántas veces cabe cada una en `rest`. El problema es que el "dígito" en cada posición debe estar acotado a `k-1` (ya que la base es `k`), pero el código calcula `v = rest // x` sin ese límite, permitiendo que se use un dígito ≥ `k`.

Verifiqué esto con el caso `test_39.txt` (fila `30 3 38158113666279`, esperado 34, obtenido 35): al llegar a la denominación `x=1` con `rest=3` y `k=3`, el código calcula `v = 3 // 1 = 3`, cuando el máximo dígito permitido es `k-1=2`. Ese exceso de 1 explica exactamente la diferencia entre 35 (obtenido) y 34 (esperado). Lo mismo ocurre en `test_06.txt` con `k=2` (dígitos deberían limitarse a 1, pero se permite mayor valor), generando las discrepancias observadas a partir de `x=10`.

La línea `rest = rest % x` está directamente acoplada a ese cálculo: si `v` estuviera correctamente acotado por `k-1`, el resto también debería calcularse como `rest - v * x` en lugar de `rest % x`.
