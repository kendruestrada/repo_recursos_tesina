###Analysis

### **Hallazgos en los logs:**

1. **Timeouts masivos**: Todos los requests terminan con `Status: timeout` después de 60 segundos (60000.00 ms)
2. **Patrón de ejecución incompleto**: Las transacciones llegan hasta el estado `ATTEMPT` en la fase 2, pero nunca alcanzan el estado `FINISH`
3. **Secuencia típica observada**:
   ```
   TXN: [ID] | SRC: [A/B] | DST: [B/A] | STATE: START
   TXN: [ID] | RES: [SRC] | PH: 1 | STATE: RESERVED
   TXN: [ID] | RES: [DST] | PH: 2 | STATE: ATTEMPT
   [TIMEOUT - Sin liberación de recursos]
   ```
4. **Ausencia de estados finales**: No se observan logs de `STATE: FINISH` ni liberación exitosa de recursos
5. **Concurrencia alta**: Múltiples transacciones ejecutándose simultáneamente entre las mismas cuentas A y B

### **Relación con el código fuente:**

El problema radica en el flujo de ejecución del archivo `transfer_funds.py`:

```python
def handler(event, context):
    # ... código inicial ...
    
    try:
        reserve_resource(f"res:{source}", tx_id)  # ✓ Reserva exitosa
        print(f"TXN: {tx_id} | RES: {source} | PH: 1 | STATE: RESERVED")

        verify_settlement_window(source)  # ⚠️ PUNTO CRÍTICO

        print(f"TXN: {tx_id} | RES: {target} | PH: 2 | STATE: ATTEMPT")
        reserve_resource(f"res:{target}", tx_id)  # ⚠️ BLOQUEO AQUÍ
        
        # ❌ NUNCA SE ALCANZA debido al bloqueo anterior
        release_resource(f"res:{source}", tx_id)
        release_resource(f"res:{target}", tx_id)
```

**Problemas identificados:**

1. **Deadlock en `reserve_resource`**: La función tiene un bucle infinito sin timeout:
   ```python
   def reserve_resource(resource_key, tx_id):
       while True:  # ⚠️ BUCLE INFINITO
           try:
               table.put_item(...)
               return True
           except ConditionalCheckFailedException:
               time.sleep(0.1)  # ⚠️ Sin límite de tiempo
   ```

2. **Timeout de `verify_settlement_window`**: Configurado con timeout de 20 segundos, pero el Lambda tiene timeout de 60 segundos
   ```python
   with urllib.request.urlopen(PROCESSOR_URL, timeout=20) as response:
   ```

### **Ejemplo de ejecución del problema:**

**Escenario**: Dos transacciones concurrentes A→B y B→A

```
Tiempo T0:
- TXN-1: Reserva "res:A" ✓
- TXN-2: Reserva "res:B" ✓

Tiempo T1:
- TXN-1: Intenta reservar "res:B" → BLOQUEADO (ya reservado por TXN-2)
- TXN-2: Intenta reservar "res:A" → BLOQUEADO (ya reservado por TXN-1)

Tiempo T2-T60:
- Ambas transacciones en bucle infinito esperando recursos
- Lambda timeout a los 60 segundos
- Recursos NUNCA liberados → Cuentas permanentemente bloqueadas
```

### **Soluciones propuestas:**

#### **Solución 1: Implementar timeout en reserve_resource**
```python
def reserve_resource(resource_key, tx_id, timeout=50):
    start = time.time()
    ttl = int(time.time()) + 300
    
    while time.time() - start < timeout:  # ✓ Límite de tiempo
        try:
            table.put_item(
                Item={
                    'resource_key': resource_key,
                    'tx_id': tx_id,
                    'timestamp': Decimal(str(time.time())),
                    'ttl': ttl
                },
                ConditionExpression='attribute_not_exists(resource_key)'
            )
            return True
        except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
            time.sleep(0.1)
    
    raise TimeoutError(f"Could not reserve {resource_key} within {timeout}s")
```

#### **Solución 2: Ordenamiento de recursos para evitar deadlock**
```python
def handler(event, context):
    # ... código inicial ...
    
    # Ordenar recursos alfabéticamente para evitar deadlock
    resources = sorted([f"res:{source}", f"res:{target}"])
    
    try:
        # Reservar en orden consistente
        reserve_resource(resources[0], tx_id)
        reserve_resource(resources[1], tx_id)
        
        verify_settlement_window(source)
        
        # Procesar transferencia
        # ...
        
        # Liberar recursos
        release_resource(resources[0], tx_id)
        release_resource(resources[1], tx_id)
```

#### **Solución 3: Mejorar manejo de excepciones**
```python
def handler(event, context):
    reserved_resources = []
    
    try:
        # ... lógica de reserva y procesamiento ...
        
    except Exception as e:
        print(f"TXN: {tx_id} | ERROR: {type(e).__name__} | MSG: {str(e)}")
        
        # Liberar todos los recursos reservados
        for resource in reserved_resources:
            release_resource(resource, tx_id)
            
        return {"statusCode": 500, "body": "Service Unavailable"}
```

#### **Solución 4: Implementar TTL automático en DynamoDB**
Configurar TTL en la tabla `TransactionTrackerTable` para auto-limpieza de recursos bloqueados:
```yaml
TransactionTrackerTable:
  Type: AWS::Serverless::SimpleTable
  Properties:
    TableName: test-016-transaction-tracker
    PrimaryKey:
      Name: resource_key
      Type: String
    TimeToLiveSpecification:
      AttributeName: ttl
      Enabled: true
```

La causa raíz es el **deadlock circular** combinado con la **ausencia de timeouts** en la reserva de recursos, causando que las cuentas queden permanentemente bloqueadas cuando hay transacciones concurrentes entre las mismas cuentas.
