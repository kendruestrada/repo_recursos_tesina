###Analysis
- **Pasos para reproducir**:
  1. Un Usuario A realiza una transacción. El contenedor Lambda se inicializa y guarda el stock actual (ej. 5) en la variable global `internal_cache['SKU-7821']`.
  2. La transacción se completa y el stock en la base de datos disminuye (ej. a 2 unidades).
  3. Un Usuario C realiza una nueva petición que recae en el mismo contenedor Lambda (warm start).
  4. La ejecución lee el valor actual de BD (`db_stock_antes = 2`), pero al existir la llave en el caché global, omite su actualización y extrae el valor obsoleto (`cached_val = 5`).
  5. El usuario intenta comprar 5 unidades. El sistema valida contra el caché (`5 >= 5`), lo cual resulta verdadero.
  6. Se calcula el nuevo stock restando la cantidad solicitada del saldo real en BD (`2 - 5`), y se guarda un stock de `-3` en DynamoDB.
- **Esperado vs. Actual**:
  Se esperaba que el sistema validara la compra usando el nivel de stock en tiempo real y detuviera la transacción si el inventario había cambiado desde que el usuario lo visualizó. En la realidad, el sistema valida utilizando un caché estático por contenedor que persiste entre llamadas, provocando un falso positivo en la validación y corrompiendo los datos (stock negativo).
- **Ubicacion del error (file/function)**:
  - Fichero: `inventory_handler/app.py`
  - Función: `lambda_handler` (uso de la variable global `internal_cache` y lógica de validación dependiente de `cached_val`).
- **Logs relevantes**:
  ```text
  --- [USUARIO: UserC] ---
  Estado DB antes: 2
  Visto en Cache: 5
  ...
  Estado DB despues: -3
  ---------------------------
  ```
### Propuesta de Solucion
1. **Eliminar el estado global (Caché en memoria)**: Remover por completo la variable global `internal_cache`. Los contenedores de Lambda son compartidos entre múltiples peticiones y usuarios, por lo que nunca deben almacenar estados de sesión o valores efímeros como el stock visualizado.
2. **Delegar el estado inicial al cliente**: Modificar el payload para que la aplicación frontend envíe la cantidad o versión del stock que el usuario tenía en pantalla al iniciar la compra (ej. `client_seen_stock`).
3. **Validación de consistencia optimista (Optimistic Concurrency Control)**: 
   - Verificar explícitamente dentro de la función que el stock reportado por el cliente coincide con el stock actual recién obtenido de Dynamo (`db_stock_antes`). Si difiere, rechazar la transacción para notificar la nueva cantidad.
   - Reemplazar la operación `table.put_item()` por un `table.update_item()` que incorpore un `ConditionExpression="stock = :expected_stock"` a nivel base de datos. Esto asegura que la reducción de inventario se realice de forma atómica y evita condiciones de carrera (Race Conditions) si ocurren transacciones exactamente al mismo milisegundo.
