### Analysis
- Pasos para reproducir:
  1. Se actualiza el precio de un producto a través de `UpdatePriceFunction`, lo que genera un evento en el Stream de DynamoDB.
  2. `CacheInvalidationFunction` recibe el lote de eventos (BatchSize configurado en 10) y procesa cada registro de manera secuencial en un ciclo `for`.
  3. Para cada evento, la función realiza una petición HTTP síncrona a un servicio externo (`requests.get(PROCESSOR_API_URL)`), el cual tarda aproximadamente 15 segundos en responder.
  4. Dado que el Timeout de la Lambda es de 20 segundos (según el archivo `template.yaml`), la función se agota y falla antes de poder procesar el resto de los registros en el lote o de alcanzar la línea que invalida la llave en Redis (`redis_client.delete(cache_key)`).
  5. El stream de DynamoDB se bloquea reintentando el lote fallido y el precio obsoleto permanece almacenado en el caché de Redis.
  6. Un cliente visualiza el producto en la interfaz obteniendo el precio desde la caché mediante `ProductPricingFunction`.
  7. El cliente intenta finalizar la compra enviando ese precio a `CheckoutFunction`, la cual delega la revisión a `InventoryCheckFunction`.
  8. `InventoryCheckFunction` lee el precio real directamente de DynamoDB, detecta que la diferencia contra el precio de la UI es mayor al margen permitido y rechaza la compra con el error "Precio manipulado o desactualizado".
- Esperado vs. Actual:
  - Esperado: Inmediatamente tras la actualización del precio en la base de datos, el caché de Redis se invalida exitosamente. Los usuarios ven el precio real actualizado y el checkout procede sin encontrar inconsistencias entre la UI y la base de datos.
  - Actual: El timeout constante en el procesamiento de eventos impide la invalidación del caché. Los usuarios siguen viendo precios antiguos y finalizan el flujo de compra enviando un monto que ya no coincide con la base de datos, generando el rechazo total de la operación.
- Ubicacion del error:
  - Archivo: `cache_invalidation/app.py`
  - Función: `lambda_handler` (específicamente la línea `response = requests.get(PROCESSOR_API_URL)` sin manejo de timeouts).
- Logs relevantes:
  - En `dev-CacheInvalidationFunction`: Tiempos de ejecución largos (15s) entre `Cambio de precio detectado...` y `Llamada a API externa completada`, seguidos de logs de caída por exceder el tiempo de vida: `REPORT RequestId: ... Duration: 20000.00 ms ... Status: timeout`.
  - En `dev-InventoryCheckFunction`: Registros que indican `[ERROR] Inconsistencia de precio detectada` con campos como `precioQueMostroCache` y `precioRealEnDB` con valores significativamente distintos.
  - En `dev-CheckoutFunction`: Registros propagados con `[ERROR] Checkout rechazado por inconsistencia de precio`.
### Propuesta de Solucion
1. Agregar un parámetro de tiempo límite en la llamada HTTP externa para evitar que bloquee el hilo principal (ejemplo: `requests.get(PROCESSOR_API_URL, timeout=2)`), capturando el posible `Timeout` en el bloque `except`.
2. Extraer la invocación a la API externa del flujo crítico de invalidación. Lo ideal es publicar un evento en SQS o EventBridge para que una función separada realice la petición HTTP de manera asíncrona, priorizando siempre limpiar Redis lo más rápido posible.
3. Procesar los registros del Stream de DynamoDB de forma concurrente en lugar de secuencial (usando hilos o `asyncio`) para mitigar bloqueos en lotes grandes de actualizaciones.
