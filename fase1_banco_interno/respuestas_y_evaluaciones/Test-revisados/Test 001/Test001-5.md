
###Analysis
## Hallazgos en los logs

Analizando los logs de CloudWatch, se identifican patrones críticos de error:

1. **Error recurrente en ProcessPurchase:**
   ```
   ERROR Purchase rejected: shipping address is missing or null
   ```

2. **Datos recibidos con address: null:**
   ```
   INFO ProcessPurchase received customer data: {"name":"Maximiliano Lopez","email":"usuario@example.com","address":null}
   ```

3. **Patrón de falla en ValidateAddress:**
   ```
   ERROR External provider error: 500 - Invalid address format
   Sync status: 200
   ```

Los logs muestran que el servicio de validación de direcciones está fallando (status 500), pero retorna exitosamente con `address: null`.

## Relación con el código fuente

### Problema 1: ValidateAddress retorna address: null
En `src/validate-address/index.js`, líneas 15-20:
```javascript
if (audit.status !== 200) {
    console.error(`External provider error: ${audit.status} - Invalid address format`);
    
    const response = {
        statusCode: 200,
        headers: { "Access-Control-Allow-Origin": "*", "Content-Type": "application/json" },
        body: JSON.stringify({ success: true, data: { name, email, address: null } })
    };
```

**Problema identificado:** Cuando el servicio externo falla, la función retorna `success: true` con `address: null`, engañando al frontend.

### Problema 2: ProcessPurchase rechaza address: null
En `src/process-purchase/index.js`, líneas 9-18:
```javascript
if (!data || !data.address) {
    console.error("Purchase rejected: shipping address is missing or null");
    return {
        statusCode: 400,
        headers: { "Access-Control-Allow-Origin": "*", "Content-Type": "application/json" },
        body: JSON.stringify({ 
            success: false, 
            error: "Invalid data context",
            receivedAddress: data ? data.address : "undefined"
        })
    };
}
```

### Problema 3: Frontend no maneja errores HTTP 400
En `frontend/index.html`, líneas 30-35:
```javascript
document.getElementById('b').addEventListener('click', async () => {
    document.getElementById('o').innerText = 'Processing...';
    const res = await fetch(`${API}/process-purchase`, { method: 'POST', body: JSON.stringify(s) });
    if (res.status === 200) {
        const r = await res.json();
        document.getElementById('o').innerHTML = '<h2>Order: ' + r.data.orderId + '</h2>';
    }
});
```

**Problema identificado:** El frontend solo maneja respuestas con status 200, ignorando completamente los errores 400.

## Ejemplo de ejecución

**Flujo actual problemático:**
1. Usuario ingresa: `name: "Juan", email: "juan@test.com", address: "Calle 123"`
2. ValidateAddress llama servicio externo → Falla (500)
3. ValidateAddress retorna: `{success: true, data: {name: "Juan", email: "juan@test.com", address: null}}`
4. Frontend habilita botón "Comprar" (porque success: true)
5. Usuario hace clic en "Comprar"
6. ProcessPurchase recibe data con address: null
7. ProcessPurchase retorna HTTP 400 con error
8. Frontend ignora la respuesta 400 → **Botón parece no responder**

## Soluciones propuestas

### Solución 1: Corregir ValidateAddress
```javascript
if (audit.status !== 200) {
    console.error(`External provider error: ${audit.status} - Invalid address format`);
    
    return {
        statusCode: 400, // Cambiar de 200 a 400
        headers: { "Access-Control-Allow-Origin": "*", "Content-Type": "application/json" },
        body: JSON.stringify({ 
            success: false, // Cambiar de true a false
            error: "Address validation service unavailable",
            data: null 
        })
    };
}
```

### Solución 2: Mejorar manejo de errores en Frontend
```javascript
document.getElementById('b').addEventListener('click', async () => {
    document.getElementById('o').innerText = 'Processing...';
    try {
        const res = await fetch(`${API}/process-purchase`, { 
            method: 'POST', 
            body: JSON.stringify(s) 
        });
        
        const r = await res.json();
        
        if (res.status === 200) {
            document.getElementById('o').innerHTML = '<h2>Order: ' + r.data.orderId + '</h2>';
        } else {
            // Manejar errores
            document.getElementById('o').innerHTML = '<p style="color:red">Error: ' + (r.error || 'Purchase failed') + '</p>';
        }
    } catch (error) {
        document.getElementById('o').innerHTML = '<p style="color:red">Network error occurred</p>';
    }
});
```

### Solución 3: Validar datos en Frontend antes de habilitar botón
```javascript
document.getElementById('f').addEventListener('submit', async (ev) => {
    ev.preventDefault();
    const res = await fetch(`${API}/validate-address`, {
        method: 'POST',
        body: JSON.stringify({
            name: document.getElementById('n').value, 
            email: document.getElementById('e').value, 
            address: document.getElementById('a').value
        })
    });
    
    const r = await res.json();
    
    if (res.status === 200 && r.success && r.data.address) { // Verificar que address no sea null
        s = r.data;
        document.getElementById('b').disabled = false;
        document.getElementById('o').innerText = 'Data synchronized.';
    } else {
        document.getElementById('b').disabled = true;
        document.getElementById('o').innerText = 'Address validation failed. Please try again.';
    }
});
```

**Causa raíz:** El servicio de validación de direcciones está fallando pero retorna éxito falso, y el frontend no maneja adecuadamente los errores HTTP, creando la ilusión de que el botón no responde cuando en realidad está recibiendo errores que ignora.
