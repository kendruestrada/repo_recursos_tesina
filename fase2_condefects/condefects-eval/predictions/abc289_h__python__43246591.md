# Análisis del Ticket

## Ticket
Se reporta que la solución falla por **timeout** (posible loop infinito) en los casos con valores de `T` grandes (>20000), mientras que los casos con `T` pequeño se resuelven correctamente. Ningún caso falla por respuesta incorrecta, solo por exceder el tiempo.

## Hallazgos en los logs
- Todos los casos `FAIL` (`02_random_02`, `03_t_max_00`, `03_t_max_02`, `04_max_width_02`, `05_no_meet_02`) reportan **timeout**, no salida incorrecta.
- Los casos `OK` corresponden a entradas con `T` pequeño (ej. `T=1`).
- Esto indica que el algoritmo es **correcto** pero tiene una complejidad mayor a la esperada, degradándose fuertemente al crecer `T` (comportamiento típico de una convolución/NTT que no está siendo truncada correctamente en un método de Newton para inversión de series de potencias).

## Relación con el código fuente
La función `fpsinv` implementa la inversión de una serie de potencias mediante el método de Newton por duplicación:

```python
def fpsinv(f,N):
    g = [pow(f[0],MOD-2,MOD)]
    n = 1
    while n <= N:
        ng = [2*i for i in g]+[0]*n
        fgg = polymul(polymul(g,g),f)
        for i in range(min(len(fgg),2*n)):
            ng[i] -= fgg[i]
            ng[i] %= MOD
        n *= 2
        g = ng
    return g[:N+1]
```

El problema está en:

```python
fgg = polymul(polymul(g,g),f)
```

En cada iteración, `g` tiene tamaño `n` (que va duplicándose: 1, 2, 4, 8, ...), pero **`f` se usa en su longitud completa (`T+1`)** en cada iteración, en lugar de truncarse a `f[:2*n]` (o `min(2*n, len(f))`).

Como la complejidad de una convolución NTT entre un arreglo pequeño y uno grande está dominada por el tamaño del arreglo **más grande**, cada iteración del bucle `while` cuesta `O(T log T)` en lugar de `O(n log n)`. Dado que hay `O(log T)` iteraciones, la complejidad total pasa de `O(T log T)` (esperado) a `O(T log² T)` (real), lo que introduce un factor extra de ~17 para `T=100000`, suficiente para provocar el timeout observado solo en los casos con `T` grande.

Esto explica perfectamente el patrón: **respuesta correcta pero demasiado lenta**, y solo en los casos de `T` grande.

## Ejemplo de ejecución
Para `T=100000`:
- `n` recorre 1, 2, 4, ..., hasta ~131072 (17 iteraciones).
- En **cada** iteración, `polymul(polymul(g,g), f)` convoluciona con `f` de tamaño `100001`, forzando una NTT de tamaño `~2^18` sin importar cuán pequeño sea `g`.
- Total: 17 convoluciones de tamaño máximo en lugar de convoluciones de tamaño creciente `n`, `2n`, `4n`... Esto multiplica el trabajo real por un factor `~log(T)`.

## Solución propuesta
Truncar `f` al tamaño necesario en cada iteración antes de la convolución:

```python
fgg = polymul(polymul(g,g), f[:min(len(f), 2*n)])
```

Esto restaura la complejidad esperada `O(T log T)` para toda la función `fpsinv`.
