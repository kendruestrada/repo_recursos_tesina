### Analysis

**Pasos para reproducir:**
1. El Lambda recibe multiples solicitudes en el mismo execution environment (warm starts).
2. Cada invocacion llama a `template()`, que incrementa `count` y agrega entradas a `TEMPLATE_CACHE`.
3. La memoria crece request a request hasta agotar los 128 MB configurados.

**Expected vs. Actual:**
- Esperado: Cada invocacion genera y retorna el PDF sin retener memoria entre llamadas.
- Actual: Cada invocacion agrega un objeto `Template` + una lista de enteros creciente a `TEMPLATE_CACHE` en memoria global. La lista crece como `N * 100,000` por invocacion, nunca se libera.

**Ubicacion del bug:**

`lambda/report.py` — hay tres problemas concretos:

**Problema 1 — Lista que crece cuadraticamente (linea 81):**
```python
my_list = [i for i in range(100000 * count)]
```
En cada invocacion, `count` sube (+1). La lista se hace N veces mas grande que la anterior.

| Invocacion | Elementos en lista | Tamano aprox. |
|---|---|---|
| 1 | 100,000 | ~0.8 MB |
| 2 | 200,000 | ~1.6 MB |
| 3 | 300,000 | ~2.4 MB |
| 4 | 400,000 | ~3.2 MB |
| 5 | 500,000 | ~4.0 MB |

**Problema 2 — Cache global sin limite ni limpieza (lineas 9 y 84):**
```python
TEMPLATE_CACHE = []   # modulo-level, persiste entre warm starts
...
TEMPLATE_CACHE.append({"template": f, "list": my_list})  # nunca se elimina
```
Cada llamada acumula en `TEMPLATE_CACHE` el objeto `Template` y la lista creciente. Los logs confirman el patron:

```
List size: 800984 bytes,   count: 1
List size: 1624056 bytes,  count: 2
List size: 2601560 bytes,  count: 3
List size: 3292664 bytes,  count: 4
List size: 4167352 bytes,  count: 5  --> CRASH: Runtime.OutOfMemory
```

Despues del crash Lambda recicla el execution environment y reinicia desde `count=1`.

**Problema 3 — Archivos PDF en `/tmp` que no se eliminan (linea 79):**
```python
f.render(f"/tmp/template_{count}.pdf")
```
Los archivos se acumulan en `/tmp` (512 MB de limite en Lambda) con nombres distintos por invocacion. Con suficientes invocaciones en el mismo environment, esto puede agotar el almacenamiento temporal.

**Evidencia de logs CloudWatch:**
- 18 errores `Runtime.OutOfMemory` en 48 horas.
- Duracion de requests escala de ~5 segundos hasta 31-34 segundos antes del crash (la GC de Python intenta liberar memoria sin exito).
- Max Memory Used = 127-128 MB en todos los crashes (100% del limite de 128 MB).
- El ciclo `count: 1 → 5 → crash → count: 1` se repite sistematicamente, confirmando que el crash reinicia el environment.

---

### Solution

**Causa raiz 1 y 2 — Eliminar `TEMPLATE_CACHE` y `my_list`:**

`TEMPLATE_CACHE` no cumple ninguna funcion real: el template se renderiza a `/tmp` y nunca se lee de vuelta desde el cache. `my_list` no tiene uso funcional alguno; es pura acumulacion de memoria. Ambas estructuras deben eliminarse de `report.py`:

```python
# Eliminar estas lineas del modulo:
count = 0          # linea 8
TEMPLATE_CACHE = []  # linea 9

# Dentro de template(), eliminar:
my_list = [i for i in range(100000 * count)]       # linea 81
print(f"List size: {sys.getsizeof(my_list)} bytes, count: {count}")  # linea 82
TEMPLATE_CACHE.append({"template": f, "list": my_list})  # linea 84
```

**Causa raiz 3 — Limpiar archivos temporales:**

Si se necesita un nombre unico para el archivo temporal, usar `uuid` o `context.aws_request_id` y eliminar el archivo al terminar:

```python
import os, uuid
tmp_path = f"/tmp/template_{uuid.uuid4()}.pdf"
f.render(tmp_path)
# ... usar el archivo si se necesita ...
os.remove(tmp_path)
```

**Causa contribuyente — Memoria Lambda insuficiente (CDK stack, linea 35):**

128 MB es extremadamente bajo para generacion de PDF con `fpdf2`. Incrementar a minimo 512 MB en `test_009-stack.ts`:

```typescript
memorySize: 512,  // era 128
```

Esto da margen ante picos de memoria durante la generacion del PDF y previene errores OOM incluso ante futuros incrementos de carga.
