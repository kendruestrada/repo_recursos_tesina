## Análisis Técnico

**Ticket:** El programa falla en **todos los casos de prueba** con la misma excepción: `ValueError: invalid literal` al ejecutar `int(input())` en la línea 11, dentro de la función `request()`. El fallo ocurre incluso en el primer caso de muestra, lo que indica que el problema no es de lógica algorítmica sino de **protocolo de comunicación interactiva**.

**Hallazgos en los logs:**
- El error se repite de forma idéntica en las 10 pruebas.
- La excepción ocurre en la **primera llamada** a `request(i)` (i=0), es decir, en la primera interacción con el juez.
- El mensaje `invalid literal` sugiere que `input()` está recibiendo una cadena vacía o no numérica en lugar de la respuesta esperada del juez interactivo.

**Relación con el código fuente:**

Este problema (ABC313 D) es de tipo **interactivo**: el programa debe imprimir una consulta (`print("?", *X)`), y el juez responde con un valor que se lee mediante `input()`. En Python, `print()` **no vacía (flush) el buffer de salida estándar por defecto** cuando la salida no está conectada a una terminal (como ocurre en los entornos de evaluación con tuberías/pipes).

```python
def request(i):
    if i <= K:
        X = [(k+i)%(K+1)+1 for k in range(K)]
    else:
        X = [k+1 for k in range(K-1)] + [i+1]
    print("?",*X)
    s = int(input())
    S.append(s)
```

Al no forzar el `flush`, la consulta `"? X1 X2 ..."` queda retenida en el buffer interno de Python y **nunca llega al proceso juez**. Como consecuencia, el juez no responde (o responde con datos desincronizados), y `input()` recibe una línea vacía o corrupta, provocando el `ValueError` al intentar convertirla con `int()`.

**Ejemplo de ejecución (simulación):**

```
Programa: print("?", 1, 2, 3)   # queda en buffer, no se envía
Programa: s = int(input())      # el juez no ha recibido la pregunta,
                                 # no hay respuesta disponible -> línea vacía
                                 # int("") -> ValueError: invalid literal
```

Este comportamiento coincide exactamente con el patrón de fallo observado: **falla siempre en la primera consulta**, sin importar el tamaño de la entrada (N, K), confirmando que es un problema de sincronización I/O y no de la lógica de reconstrucción del arreglo `A`.

**Solución propuesta:**

Agregar `flush=True` a la llamada de `print` que envía la consulta al juez, o forzar `sys.stdout.flush()` inmediatamente después:

```python
print("?", *X, flush=True)
s = int(input())
```

Esto garantiza que la consulta se envíe inmediatamente al juez interactivo antes de bloquear la ejecución esperando la respuesta con `input()`.
